# 架構決策記錄 (Architecture Decision Records, ADR)

本目錄存放本專案所有關鍵架構、技術選型、模組拆分與治理方針的**架構決策記錄 (ADR)**。

---

## 💡 為什麼需要 ADR？
在軟體開發與專案演進中，最昂貴的成本往往不是寫程式碼，而是**「忘記當初為什麼這樣做」**或**「不知道為什麼當時否決了另一種做法」**。
ADR 能達到以下效益：
1. **保留設計上下文 (Context)**：清楚記錄當時的業務需求、環境限制與技術背景。
2. **多方案優缺點比對 (Trade-offs)**：誠實記錄「評估過哪些替代方案」，以及「各自的優缺點是什麼」。
3. **終結無效爭論與 AI 記憶漂移**：未來接手的工程師或 AI 代理人能迅速理解歷史決策邊界，不踩重複的坑。

---

## 🚦 ADR 生命週期狀態 (Status)
每一篇 ADR 都會有以下幾種明確狀態：
- **`提議中 (Proposed)`**：方案已提出並分析優缺點，正等待架構師/維護者確認。
- **`已採納 (Accepted)`**：決策已經過確認，正式納入實作規範。
- **`被取代 (Superseded by ADR-xxxx)`**：隨著技術演進，舊決策已被新的 ADR 取代。
- **`已廢棄 (Deprecated)`**：該架構方案已不再適用。

---

## 📝 如何新增 ADR？
1. 複製 `docs/adr/template.md`，命名為 `docs/adr/XXXX-短標題-以連字號分隔.md`（例如 `0002-cache-storage-selection.md`）。
2. 詳細填寫 **背景痛點**、**負面邊界 (Negative Constraints)**、**備選方案優缺點比對** 與 **最終決策理由**。
3. 更新下方「決策索引清單」。
